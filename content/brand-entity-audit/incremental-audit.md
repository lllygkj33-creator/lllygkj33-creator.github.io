> 全站扫描是一次性动作，增量扫描才是长期运行方式。判断"这个页面要不要重抽"需要三个判据，判断"知识库要不要改"需要抽样 QA——**前者省钱，后者防错，两件事不能互相替代**。

## 先分清两个不同的问题

很多团队把增量扫描理解成"少跑几页"。这是把两个问题混成一个：

| 问题 | 在问什么 | 回答它的机制 |
| --- | --- | --- |
| 这个页面变了吗？ | 页面文本是否与上次抽取时不同 | content_hash / last_modified / template_version |
| 这个知识还对吗？ | Canonical Fact / Claim 是否仍然成立 | 抽样 QA + Dependency Impact |

第一类问题可以用机器判断，代价接近零。
第二类问题不能靠"页面变了没有"回答——因为**页面完全可以一个字都没改，而它引用的知识已经错了**。

增量扫描解决第一类问题，抽样 QA 兜住第二类。少了任何一个，系统都会失灵。

## 三个判据各自解决什么

只看一个字段一定会误判。三个判据是三件不同的事：

| 判据 | 回答的问题 | 单独使用时的问题 |
| --- | --- | --- |
| **content_hash** | 正文内容有没有真的变化 | 改一个模板 className 也会让 hash 变，产生无用重抽 |
| **last_modified** | 网站自称什么时候更新过 | 只能当提示，不能当证据：改过但没更新时间和没改但刷新时间，两种情况都很常见 |
| **template_version** | 页面外壳有没有换版 | 只管结构，不管内容，必须和 content_hash 一起用 |

三者组合的判断逻辑：

```text
content_hash 变 + 正文区没变
→ 模板或全局组件变化
→ 不重抽，只刷新 template_version 与正文选择器

content_hash 没变 + last_modified 变了
→ 时间戳刷新或页面被重新生成
→ 不重抽，但记一次"疑似刷新"

content_hash 变 + 正文区变了
→ 真实内容变化
→ re-extract

三者都没变
→ unchanged
→ skip
```

关键点在"**正文区**"三个字。content_hash 不应该对整个 HTML 计算，而应该只对清理后的正文容器计算：

```text
抓取 HTML
↓
定位正文区域（去掉导航 / 页脚 / 推荐位 / 弹窗 / 追踪脚本）
↓
归一化（去空白、统一大小写、去掉动态时间戳）
↓
对正文文本计算 content_hash
```

如果对整页 HTML 算 hash，站群改一次页脚，5000 个页面会同时"变化"，增量扫描当场失效。**归一化不是可选项，它是增量扫描能不能用的前提。**

## 一次扫描的实际流程

```text
读取 URL 清单（sitemap.xml / CMS 导出 / Shopify 导出）
↓
逐个取回上次记录
    last_modified
    content_hash
    template_version
↓
本轮抓取（可以只抓头部拿 last_modified，正文按需抓）
↓
判定
    ├─ unchanged  → skip，只更新 last_seen
    ├─ 仅模板变化 → 刷新 template_version，不重抽
    └─ changed    → re-extract（规则抽取 + AI 抽取）
                       ↓
                   生成 Page Observation
                       ↓
                   与 Canonical 比对
                       ↓
                   Conflict Queue / Dependency Index 更新
↓
抽样 QA（即使全部 unchanged 也要跑）
↓
输出本轮报告
```

这里的 `unchanged → skip` 和 `changed → re-extract` 是整个增量的骨架。第一轮全量抓取之后，日常运行就只剩这条路径：

```text
5000 pages
↓
今天只有 47 个 content_hash 变化
↓
只对 47 个页面做 AI 抽取与比对
```

**AI 抽取是整个流程里最贵的一步**，所以增量的收益实际上就是把 AI 成本从"与页面总数成正比"降到"与当日变化数成正比"。第一轮全量扫描该花的钱必须花，之后才谈得上省钱。

## skip 不等于不作数

`skip` 的准确含义是"这一轮不需要重新抽内容"，而不是"这个页面已经安全"。被 skip 页面仍然参与三件事：

| 仍然要做的 | 原因 |
| --- | --- |
| Dependency Index 比对 | 知识变了一侧，用索引反查受影响 URL，不依赖页面是否变化 |
| 抽样 QA | 抽样要主动覆盖 skip 的页面，否则永远发现不了语义漂移 |
| 状态与时效标记 | 页面长期 unchanged 本身是信号：可能已经过期，也可能已经下架 |

第三行最容易被忽略。一个改都没改过的旧 Blog，它的 hash 永远稳定，但里面的产品版本、价格、兼容列表可能早就过时。这类页面的问题是**陈旧**，不是**变化**——靠 hash 永远不会暴露它，只能靠 freshness / version 检查。

ZimaSpace Pilot 里已经出现过这种情况：一篇标注为 `historical_sample` 的会员日活动 Blog，抽出的 Claim 状态是 `historical_claims_needs_freshness_check`。它没有被改动，也不需要重抽，但它不能被当作当前的品牌主张使用。

## 抽样 QA 的真正目的

如果一个团队只做 hash 比对，系统会长期给出"一切正常"的结论。抽样 QA 就是为了打破这个假象。

抽样不是为了省钱——**恰恰相反，它要多花钱**。它的目的是发现那些 hash 变了也发现不了的问题：

```text
页面文本没变
+
Canonical Knowledge 改了
=
页面上写的内容现在与标准答案冲突
```

这个冲突不会触发任何 hash 变化，因为页面那一侧根本没动。唯一的发现路径是：知识改动之后，主动去重新核对一批页面。

抽样由四类组合而成，各自负责不同的漏检面：

| 抽样类型 | 怎么选 | 主要发现什么 |
| --- | --- | --- |
| **高风险页面** | 承载核心 Fact / Claim 的页面：产品页、PDP、规格页 | 版本、规格、命名这类一旦错就影响面很大的错误 |
| **随机样本** | 从全站按固定比例随机抽 | 未知类型的错误，防止系统只盯着自己已知的问题 |
| **最近更新** | 最近 N 天内 last_modified 变化或内容变化的页面 | 新增内容里混进来的新 Claim、新实体候选 |
| **异常页面** | 抽取失败、正文选择器命中为空、实体数突然变化、字段缺失 | 抓取层与选择器层的技术故障 |

四类都不可省，因为它们的失效率不一样：

- 只抽高风险页面，会漏掉大量普通页面的共性问题；
- 只做随机抽样，样本太薄，核心页面的错误会被淹没；
- 只看最近更新，等于假设旧页面不会错，而旧页面恰恰最容易过期；
- 不做异常页面抽查，技术性漏抓会被当成"这个页面没有问题"。

**随机样本必须真的随机，并且比例固定**。如果每次抽样都由人挑，抽样就退化成了抽查，制度性的保障就没了。

## 抽样批次要覆盖 skip 的页面

这一点值得单独说，因为它和直觉相反：

```text
抽样池 = 本轮 changed 页面 ∪ 本轮 unchanged 页面
```

如果抽样只从 changed 页面里抽，那抽样的结论就是"变化的内容有没有被正确处理"——这只验证了流程，验证不了知识。
要发现"hash 没变但语义已错"，样本必须包含**本轮被 skip 的页面**。

可以把一轮抽样配成大约这个形状：

```text
高风险页面      固定清单，每轮都抽
随机样本        按固定比例从全站抽，含 skip 页面
最近更新        本轮 changed 页面，全量或高比例抽
异常页面        本轮抓取异常的页面，全部抽
```

## 知识侧的变化要单独走一遍

页面侧的变化由 hash 判断，知识侧的变化由 Dependency Index 判断。这是两条独立的触发路径：

```text
页面侧：content_hash 变化 → re-extract → 比对
知识侧：Canonical Fact / Claim 变化 → 查 used_by → 得到受影响 URL
```

第二条路径不重新抓取页面。它查的是依赖索引：

```sql
SELECT url, observed_value, comparison_status
FROM page_observations
WHERE canonical_id = 'F_ZB2_832_RAM';
```

这正是 Dependency Impact 那一层的职责，也是"以后不需要重新扫描全站"这句话的真正落点：

```text
5000 pages
↓
Canonical 里一条事实改了
↓
索引反查出引用它的 N 个 URL
↓
只重核对这 N 个
```

注意反查出来的 URL 只是**候选受影响集合**，不是冲突清单。页面引用同一条事实，不代表它一定与新的标准答案矛盾——尤其是当这条事实的 scope 是 variant 而页面说的是 model 层级时，结果可能是 `less_specific` 而不是 `conflict`。判断仍然要按比对规则做，不能因为"出现在受影响列表里"就标成冲突。

## 三个判据不能省掉任何一个

把上面的内容收成一条判断链：

```text
先看内容有没有真的变（content_hash）
→ 排除模板与外壳造成的假变化（template_version）
→ 用 last_modified 作为交叉提示，不作证据
→ unchanged 的页面 skip，但仍然进抽样池
→ 知识侧变化另走 Dependency Index 反查
→ 每轮抽样都必须包含 skip 页面
```

一句话总结：**增量扫描决定"哪些页面要重抽"，抽样 QA 决定"我们有没有把问题想漏"。** 前者是效率机制，后者是质量机制，缺了后者的系统会非常安静，而安静不等于正确。
