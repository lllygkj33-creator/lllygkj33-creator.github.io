> **一条知识改了，要回答的不是「全站现在什么样」，而是「哪些页面引用了这条知识」。** 前者要重扫全站，后者查一次索引就够。做法很简单：抽取时顺手记下每个页面引用了哪条知识。

## 索引的形状

索引只记一件事：哪个页面引用了哪条知识。所以形状是三层，从页面往下走到事实。

| 层 | 记什么 | 回答什么 |
| --- | --- | --- |
| 页面 | 页面类型、最近修改时间 | 哪些页面最近改过 |
| 页面 → 实体 | 这个页面涉及哪个实体 | 哪些页面涉及这个实体 |
| 页面 → 事实 / 主张 | 引用了哪条事实或主张、当时观测到什么值 | **这条知识改了，影响哪些页面** |

事实管「它是什么」，主张管「它能做什么、适合什么」。两者共用同一套索引结构，但分成两条引用链分别存放。

三条记录就能说明它的样子：商城产品页引用了变体内存这条事实，产品 Blog 引用了同一个产品的内存类型，AI 场景 Blog 引用了「可以运行 Plex」这条能力主张。它们都以同一个形状存下来，只是引用的目标不同。

分层不是为了好看。合成一个巨大的文件，任何一次查询都要读整份；分开之后，一条知识的关联查询只碰到最后一层。实体层还顺便回答另一个问题：哪些页面在讲某个实体，却一条规格都没引用。

## 一次查询拿到清单

起点、关系、终点都是已知的，所以这只是一次两跳关联查询。

```sql
SELECT source_id, page_type, observed_value, comparison_status
FROM page_ref JOIN page USING (source_id)
WHERE ref_id = 'F_ZB2_832_RAM'
ORDER BY page_type;
```

结果里除了页面名单，还带着这个页面当时写的值和它的比较状态。这意味着不需要先查名单、再逐页打开核对，派工单和现象是同一行。

换成另一个起点也一样：把 `ref_id` 换成一条能力主张，拿到的就是引用这条主张的页面。差别只在于这些页面要改的是措辞，不是规格数字。

## 为什么不用图数据库

图数据库擅长未知起点、未知跳数、需要给路径打分的问题，比如两个实体之间有哪些间接关联路径。我们这里的起点、关系、终点全部已知，上图的收益是零，成本是长期多养一套存储和服务。

```text
SQLite 够用
√ 单文件，零运维
√ 建好索引后，join 是毫秒级
```

## 场景：把 8GB 改成新值

假设品牌侧确认 8GB 这条内存事实的值需要更新，接下来只有三件事。

第一件是查名单：一条查询立即返回受影响页面 3 个。其中 PDP 页面给的是完整规格写法，产品 Blog 写的是简写，支持文档的表述也需要同步。名单是闭集，不再需要靠猜哪里可能写过这条规格。

第二件是定优先级：PDP 要确认规格对齐，Blog 要补精度或改口径，支持文档要复核。页面类型决定谁先动，值互斥的排在措辞差异前面。

第三件是回填：这三页重新抽取后更新引用记录，状态回到「一致」或「兼容」，队列才会真的变短。没有这一步，同一批问题会在下一轮增量里原样再出现一次。

重新抽取和更新索引必须落在同一次写入里。只更新了页面观察而忘了引用记录，索引就开始说谎。
