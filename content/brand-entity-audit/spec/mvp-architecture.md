> 5000 页面的品牌实体检测，**SQLite 就够了**；这是一套数据量很小、但流程要求很严的系统。

## 数据量先摆出来

选型前把数字摆出来，很多"得上分布式"的直觉会当场消失。

| 项目 | 规模 |
| --- | ---: |
| 页面 | 5000 |
| 自有实体 | 20–50 |
| 标准知识（事实与主张） | 几百条 |
| 每轮需要重抽的页面 | 当天变化的那几十页 |

这个量级落到单文件数据库里只有几千行到几十万行，关系库足够用。

瓶颈在人这一侧：Schema 设计、比对规则、审核队列怎么排，都不因为换了数据库而变简单。

抓取只负责把页面拿下来，能拿到 CMS 导出的原始数据，就不必为了技术感重新爬自己的网站。

这种场景下 Firecrawl 一类工具不是必需，它擅长的是登录页、强 JS 渲染和托管式批量爬取。

理解层的原则是规则优先：JSON-LD、规格表、结构化字段直接读，LLM 只补自然语言里的主张。

这一步产出的都只是候选，没有人工确认过的东西进不了标准知识。

## 每层交出什么

| 层 | 交出什么 |
| --- | --- |
| 抓取 | 干净的正文、来源路径、抓取时间 |
| 理解 | 候选实体、候选属性值、候选主张，每条带来源定位 |
| 存储与检查 | 审核状态、比较结果、受影响页面清单 |

候选和标准知识必须能一眼分开，否则审核会退化成"确认 AI 说的都对"。

## 存储只分两张表

**Canonical 表**存标准知识：谁、什么属性、标准值、适用范围、审核状态。

**Observation 表**存页面实际说了什么，另外留一行指向它引用了哪条标准知识。

两者语义不同，页面抽取结果绝不能直接写进 Canonical 表，这是整套系统最容易崩的地方。

链接关系也只有一条：页面 → 实体 → 事实与主张，反查受影响页面靠的就是这一条。

审核侧只多一张队列视图：谁提出、依据哪条来源、现在卡在哪个状态，人确认过才写入标准知识。

判断标准很直接：如果它解决的是规模问题或实时问题，而当前既没有规模也没有实时，它就是负债。

抓取是每天一轮的批处理，依赖反查是一次索引命中，图上看起来复杂的关系在这里本来就是单跳。

<div class="bae-note" data-tone="info"><b>什么时候才值得上图数据库</b>：出现多跳查询（要连跳几层才能回答一个问题）、需要图算法（最短路径、连通分量）、或需要可视化探索时，升级才有意义。</div>

## 落地顺序

先定两张表的 Schema，再把品牌站跑成第一批标准知识，最后才优化抓取。

品牌站内部本来就可能互相冲突，这一步不需要等扫完 5000 页才能看到结果。

界面也只要最普通的一层：列出待审条目，看得到预期值、实际值和来源，然后确认或驳回。

存储用单文件库还有个实际好处：整个过程记录可以直接拷走、离线打开检查，不需要先装好一套服务端。

这一层搭好之后，换掉抓取方式或者换掉抽取模型，都不会影响已经确认过的标准知识。
