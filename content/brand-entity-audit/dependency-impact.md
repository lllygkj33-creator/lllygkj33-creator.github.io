> **知识一变，问题不是"全站哪些地方写错了"，而是"哪些页面引用了这条知识"。** 前者的答案是"重新扫一遍 5000 页"，后者的答案是一条索引查询。把引用关系在抽取时就存下来，一条 SQL 就能拿到受影响的来源页清单，并立刻排出处理顺序。

## 先讲直觉：为什么不能全站重扫

假设品牌站某条规格被确认改动了。你的第一反应可能是"重新跑一遍全站，看看哪些页面和新规格不一致"。

这个做法有两个问题：

| 问题 | 说明 |
| --- | --- |
| 慢 | 5000 页全量抓取 + 全量 AI 抽取，成本和时间都不小 |
| 答非所问 | 你要的不是"全站现在什么样"，而是"哪些页面引用了这条被改掉的知识" |

更关键的是**第二次改动**。如果每次改动都要全站重扫，那这套系统一周只能用一次，无法进入日常运营。

正确的直觉是反过来想：**抽取的时候，我就知道这个页面引用了哪一条知识。** 那就顺手记下来。

```text
抽取时多写一行关联记录
↓
知识变化时少扫全站 100 遍
```

这就是 Dependency Index 的全部思想。它不复杂，只是一个**在写入时建立的引用表**。

## 一句话原理

```text
Fact / Claim ID  →  used_by  →  URLs
```

反过来读更清楚：

```text
这条知识被哪些页面引用了？
→ 这就是"知识变化后立刻要知道"的答案
```

## 索引的索引结构

三层，每层各管一件事。**不要把它们合成一个巨大的 JSON**，否则任何一次查询都得读整份文件。

```text
Dependency Index
│
├─ ① page 层：页面是什么
│     source_id  · url · page_type · last_modified · content_hash
│
├─ ② page_entity 层：页面涉及哪个实体
│     source_id  · entity_id · entity_status
│                        ├─ managed
│                        ├─ external_context
│                        └─ new_entity_candidate
│
└─ ③ page_ref 层：页面引用了哪条知识（核心）
      source_id  · ref_type(fact|claim) · ref_id
                 · observed_value · scope · comparison_status
```

三层里只有第 ③ 层是"秒查"的关键。它回答的是：

```text
F_ZB2_MEMTYPE
↓ used_by
SHOP_PDP_ZB2  ·  BLOG_ZB2_AI  ·  BLOG_MEMBER_DAY_2025  ·  ...
```

一层层读下来就是完整的路径：

```text
Page  →  Entity  →  Fact / Claim
```

| 层 | 解决的问题 | 典型查询 |
| --- | --- | --- |
| page | 这个页面的上下文与新鲜度 | "哪些页面最近改过？" |
| page_entity | 页面上有哪些实体、各自什么身份 | "哪些页面涉及这个实体？" |
| page_ref | 页面引用了哪些知识、当前是否一致 | **"这条知识改了，影响哪些页面？"** |

## 为什么一条查询就够

因为这是一次**已知起点的关联查询**，不是路径搜索。

```text
起点已知：fact_id = 'F_ZB2_MEMTYPE'
关系固定：page_ref 表里的直接引用
终点明确：source_id → url
```

中间不需要"找路径"、不需要"多跳推理"、不需要"社区发现"。SQL 天然擅长这种固定两跳的关联查询：

```sql
SELECT r.source_id, p.url, p.page_type, r.observed_value, r.comparison_status
FROM page_ref r
JOIN page p ON p.source_id = r.source_id
WHERE r.ref_type = 'fact'
  AND r.ref_id = 'F_ZB2_MEMTYPE'
ORDER BY p.page_type;
```

跑出来的就是一张可以直接派工的清单（`observed_value` 与 `comparison_status` 示意）：

| source_id | page_type | observed_value | comparison_status |
| --- | --- | --- | --- |
| SHOP_PDP_ZB2 | pdp | 完整内存写法 | match |
| BLOG_ZB2_AI | blog | 简化内存写法 | conflict |
| BLOG_MEMBER_DAY_2025 | blog | 沿用旧口径 | match |

一次查询，名单到手。**这就是"秒查"的全部含义**——不是算得快，而是**根本不用重新爬**。

## 为什么不需要图数据库

这是最常被过度设计的一步。先看清需求：

| 需求 | 用得上图数据库吗 |
| --- | --- |
| 一条知识 → 引用它的页面 | 不用，两跳 join |
| 一个实体 → 相关页面 | 不用，一次 group by |
| 批量改动 → 受影响清单 | 不用，`IN` 列表 |
| 冲突页面之间是否存在传导关系 | 不需要做，这不是第一版的问题 |

图数据库擅长的是**未知起点、未知跳数、需要路径评分**的问题——比如"这两个实体之间有哪些间接关联路径"。我们这里的起点、关系、终点全部已知，用图数据库等于为了一个 join 引入一套独立的存储与服务。

5000 页面规模下：

```text
SQLite 足够
√ 单文件、零运维
√ 索引建好，join 是毫秒级
√ 数据可导出、可 diff、可版本化
```

这也符合整套系统的一贯取舍：**先用 JSON + SQLite 把流程跑通，再考虑知识图谱与图数据库。** 第一版上 Neo4j 这类方案，收益是零，成本是长期运维。

## 完整链路：从一次改动到一张工单

用一个具体场景走一遍。

### 场景

品牌侧确认：某条 Canonical 事实的值需要更新（例如某个属性的规格写法被修正），这条事实的 ID 是已知的。

### 第 1 步：查出引用它的页面

```sql
SELECT source_id, url, page_type, observed_value, comparison_status
FROM page_ref
WHERE ref_id = 'F_ZB2_MEMTYPE';
```

### 第 2 步：对照新旧值，判断每个页面的处理动作

不是所有受影响的页面都要动。要区分"和新值一致""和新值不一致""需要补精度"：

| 页面 | 页面当前写法 | 相对新值的状态 | 处理动作 |
| --- | --- | --- | --- |
| 商城规格页 | 完整写法 | 需要复核 | 确认后按新值统一 |
| 产品相关 Blog | 简化写法 | 需修正 | 补精度或改口径 |
| 历史活动文章 | 沿用旧口径 | 需加时效上下文 | 加更新说明，不硬改历史 |
| 其他引用页 | 与旧值一致 | 需复核 | 逐条确认后再改 |

### 第 3 步：按优先级排序派工

排序不是拍脑袋，用几条固定规则叠加（示例权重，可按团队调整）：

| 优先级因子 | 高 | 低 |
| --- | --- | --- |
| 不一致类型 | 值互斥 | 精度不足 / 措辞差异 |
| 页面类型 | PDP / 规格页 | Blog / 历史文章 |
| 页面角色 | 入口页 / 主推页 | 长尾页 |
| 引用集中度 | 一条知识被很多页引用 | 只被个别页引用 |

排完序就是一张可以逐行勾掉的工作清单，而不是一个"看起来有三百条问题"的恐慌列表。

### 第 4 步：改完回填，验证闭环

```text
改动 → 重新抽取受影响页面 → 更新 page_ref
→ comparison_status 转为 match / compatible
→ 队列条目关闭
```

这一步很重要：**只有回填了，队列才会真的变短。** 否则同一批问题会在下一轮增量里原样再出现一次。

## Fact 与 Claim 要分两条依赖链

不能只建一张 fact 引用表。Claim 同样会被来回改动，而且它的改动方式不同：

| | Fact 改动 | Claim 改动 |
| --- | --- | --- |
| 什么会变 | 值、单位、精度、Scope | 措辞强度、适用条件、推荐范围 |
| 典型影响 | 规格页、参数表 | 场景页、推荐段、对比段 |
| 特别注意 | 变体级与型号级不可混改 | `can_run` 不得因为改动被抬成 `best_for` |
| 索引字段 | `ref_type = 'fact'` | `ref_type = 'claim'` |

两条链**结构相同、词表不同、处理队列也不同**。混在一张表里，就会出现"改一条能力声明的措辞，结果把规格页也一起拉进队列"这种噪音。

## 三个容易做错的地方

### 1. 多值属性被压成一个 ID

有些属性本身就是一组值（例如一份兼容系统清单）。如果只存一个 `ref_id`，那么清单里**某一项**变化时，你无法定位到具体是哪个页面引用了那一项。

```text
坏做法：ref_id = F_ZB2_COMPAT_OS        （整条清单一个 ID）
好做法：按选项粒度存引用，或对值做 hash + 保留人工复核
```

拆到选项粒度之后，清单里增加一项，你查到的就是"列了这一项的页面"和"应该列但没列的页面"两份名单，而不是"所有引用过兼容系统这件事的页面"。

### 2. 漏掉"应该引用却没有引用"的页面

Dependency Index 只能回答"谁引用了"。它回答不了"谁应该引用而没引用"。

```text
能查：F_ZB2_MEMTYPE → 引用它的页面
查不到：讲同一个产品但完全没提这条规格的页面
```

补法是**用反向计数**：统计每条知识被多少个页面引用，再把结果和实体维度交叉。某条事实被引用的页面数明显偏低，说明这一类页面整体缺规格引用——这是覆盖面问题，不是冲突问题，要单独进一个队列。

### 3. 索引和观察不同步

如果页面重新抽取了，但 `page_ref` 没更新，索引就开始说谎：你会以为某页还引用着旧值，实际上它早就改了。

规则很简单：**重新抽取与索引更新必须在同一次写入里完成。** 观察更新了而索引没更新，等于索引不可信；索引不可信，这篇讲的所有"秒查"都不成立。

## 结论

- **Dependency Impact 回答的是"知识变化 → 受影响 URL"**，不是"全站现在什么样"。想清楚这一点，全站重扫就不必要了。
- **核心是三层索引**：`page` 管上下文，`page_entity` 管实体与身份，`page_ref` 管引用关系。秒查靠的是第 ③ 层。
- **一条 SQL 就够**，因为它是一次起点已知、关系固定的两跳 join，不是路径搜索。
- **5000 页面规模用 SQLite 足够**，第一版不需要图数据库；图数据库解决的是路径类问题，不是引用计数类问题。
- **Fact 与 Claim 分成两条依赖链**，结构相同、词表不同、队列不同。
- **改完必须回填索引**：只有 `comparison_status` 回到一致，队列才真的变短。

整套流程到这里就闭合了：**抽取产生 Observation，比较产生状态，状态进人工队列，人工确认后更新 Canonical，索引算出受影响页面，页面修正后再回到 Observation。** 一个知识变化从被发现到被处理完，全程不需要重新扫全站。
