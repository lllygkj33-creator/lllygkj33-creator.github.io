> Freshness 的核心不是“页面越新越好”，而是：**当用户的问题需要最新信息时，页面必须持续提供当前、准确、可验证的答案。**

## 什么是 Freshness

Google 并不会因为页面发布日期更近就自动给更高排名。真正需要判断的是：这个 Query 是否具有明显时效性，以及页面里的事实是否已经发生变化。

| Query 类型 | Freshness 重要度 | 示例 |
| --- | ---: | --- |
| 突发新闻 | 极高 | OpenAI 发布新模型 |
| 软件版本 | 高 | Ubuntu 26.04 安装方法 |
| 产品价格 | 高 | RTX 6090 当前价格 |
| 年度榜单 | 高 | Best NAS 2026 |
| 兼容性 | 中高 | 某设备是否支持新协议 |
| Evergreen 教程 | 中 | How RAID Works |
| 基础定义 | 低 | What Is DNS |
| 历史事实 | 低 | PageRank 早期原理 |

Freshness 的判断对象是：

```text
Query
+
事实变化速度
+
用户对“最新”的期待
```

## 哪些页面该更新

优先级应该由“错误风险”和“流量价值”决定，而不是所有页面一起刷新。

| 页面情况 | 优先级 |
| --- | ---: |
| 排名高但事实已过时 | ★★★★★ |
| 高流量、强商业价值 | ★★★★★ |
| 软件 / 产品版本频繁变化 | ★★★★★ |
| 核心 Pillar Page | ★★★★☆ |
| 排名 5–20 且内容明显旧 | ★★★★☆ |
| 长尾低流量但高风险 | ★★★★☆ |
| 历史归档 | ★★☆☆☆ |
| 几乎无搜索需求 | ★☆☆☆☆ |

可以建立内部模型：

```text
Update Priority
=
Traffic Value
×
Freshness Need
×
Fact Change Risk
×
Business Importance
```

这不是 Google 官方公式，只用于排期。

## 真更新和假更新

| 操作 | 是否算有效更新 |
| --- | --- |
| 新增新版本规格 | 是 |
| 修正过时数据 | 是 |
| 重做结论 | 是 |
| 增加实测结果 | 是 |
| 更新截图与步骤 | 是 |
| 改发布日期 | 否 |
| 换几个同义词 | 否 |
| 增加无意义 FAQ | 否 |
| 把 2025 改成 2026 | 否 |
| 调整几个标点 | 否 |

最危险的做法是：

```text
Updated: 2026
```

但正文仍然引用：

```text
2024 年旧规格
旧价格
旧版本
旧兼容性
```

这会破坏 Trust。

## 更新前检查

更新一篇旧页面前，先做四层检查。

| 层级 | 检查 |
| --- | --- |
| Query | 搜索意图是否变了 |
| SERP | 排名页面类型是否变了 |
| Content | 哪些事实过时 |
| Competition | 新竞争页新增了什么 |

不要直接打开旧文然后改句子。先确认：

```text
过去用户要什么
vs
现在用户要什么
```

## Query 是否变了

例如：

```text
home server
```

两年前可能 SERP 偏：

```text
DIY tutorial
```

后来可能变成：

```text
mini PC
NAS
Reddit
AI home server
```

如果意图已经变化，仅更新年份不够，页面结构也要调整。

建议记录：

| 项目 | 旧状态 | 当前状态 |
| --- | --- | --- |
| 主 Intent | Informational | Commercial Investigation |
| Top 10 类型 | Blog 为主 | Blog + Reddit + Product |
| PAA | 旧问题 | 新问题 |
| 新实体 | 无 | Local AI / NPU |
| 决策点 | CPU / RAM | GPU / AI / Power |

## 事实更新时间

页面里的信息可以按“变化速度”分层。

| 信息 | 建议检查频率 |
| --- | --- |
| 产品价格 | 高频 |
| 软件版本 | 高频 |
| API / 参数 | 高频 |
| 兼容矩阵 | 高频 |
| Benchmark | 新版本时 |
| 标准协议 | 中频 |
| 基础原理 | 低频 |
| 历史背景 | 极低 |

不要用统一的：

```text
每 90 天更新所有文章
```

不同页面需要不同周期。

## 更新时间怎么显示

推荐显示：

```text
Published
Updated
```

但 Updated 只有在发生实质变化时才修改。

例如：

| 变化 | 是否更新 Updated |
| --- | --- |
| 新增新版本 | 是 |
| 修改关键结论 | 是 |
| 新增测试数据 | 是 |
| 修复严重事实错误 | 是 |
| 改错字 | 通常否 |
| 调整格式 | 否 |

如果页面涉及高风险事实，还可以显示：

```text
Last Reviewed
```

用于说明最后一次专业核查时间。

## 年份标题怎么处理

不要为了每年搜索量创建大量重复 URL。

容易蚕食：

```text
/best-nas-2024
/best-nas-2025
/best-nas-2026
```

Evergreen 主题更适合：

```text
/best-nas
```

页面内更新：

```text
Best NAS in 2026
Updated September 2026
```

只有年份本身构成独立实体时才保留独立 URL。

| 场景 | 独立年份 URL |
| --- | --- |
| CES 2026 | 是 |
| Apple Event 2026 | 是 |
| Best NAS 2026 | 通常否 |
| Tax Rules 2026 | 视法规结构 |
| Annual Report 2026 | 是 |

## 更新时保留什么

不要为了“重写”把原页面所有内容推倒。

优先保留：

- 已排名段落
- 已获得外链的独特数据
- 历史高点击 Query 对应内容
- 用户仍然需要的稳定结论
- 已建立实体关系的核心部分

更新目标是：

```text
保留有效资产
+
替换过时信息
+
补新问题
+
删除失效段落
```

## 删除旧内容

不是所有旧内容都值得更新。

| 情况 | 处理 |
| --- | --- |
| 仍有搜索需求 | 更新 |
| 两篇同 Intent | 合并 |
| 有替代页面 | 301 |
| 无价值且无信号 | 删除 / 410 / 404 |
| 历史有参考价值 | 保留并标注 |
| 完全过时且危险 | 优先下线 |

不要为了所谓“Content Pruning”大规模删除仍有价值页面。

## Freshness QA

| 检查项 | 合格标准 |
| --- | --- |
| Query 时效性 | 已判断 |
| 事实状态 | 当前有效 |
| 版本 | 与正文一致 |
| 数据 | 有时间标记 |
| Screenshot | 与当前界面一致 |
| Links | 没有失效来源 |
| Updated | 与实质更新一致 |
| Conclusion | 与当前环境一致 |
| SERP Intent | 已重新确认 |
| Internal Links | 指向当前版本 |

## 核心规范

```text
先判断 Query 是否需要新鲜度
→ 再判断哪些事实已经变化
→ 再更新答案和结构
→ 最后修改更新时间
```

> **Freshness 不是“让页面看起来新”，而是保证时间敏感的 Query 始终得到当前答案。真正有效的更新，必须改变事实、结论、证据或用户任务覆盖，而不是只改日期。**
