> 来源的价值不在数量，而在：**它是否直接支持当前 Claim、是否独立、是否足够权威，以及是否仍然有效。**

## 为什么要分级

不同 Claim 对证据要求不同。

| Claim | 推荐证据 |
| --- | --- |
| 产品有 2 个 HDMI 2.1 | 官方规格 |
| 240Hz 帧间隔约 4.2ms | 数学 / 技术事实 |
| 某 GPU 推理更快 | 同条件 Benchmark |
| 某设置减少故障 | 一手测试 + 多源验证 |
| 某疗法有效 | 高等级医学证据 |
| 某产品“最好” | 多维比较 + 明确条件 |

内部原则：

```text
Claim Strength
≤
Evidence Strength
```

## 证据等级

可以建立统一等级。

| 等级 | 来源类型 | 适合 |
| --- | --- | --- |
| A | 官方标准、政府、原始研究 | 强事实、高风险 Claim |
| A | 官方产品文档、原始规格 | 产品事实 |
| A | 一手 Benchmark / 自有测试 | 性能 Claim |
| B | 大学、专业组织、权威机构 | 专业解释 |
| B | 多个独立高质量来源 | 共识 |
| C | 高质量行业媒体 | 背景、趋势 |
| C | 资深专家公开观点 | 解释 |
| D | Reddit、Forum、评论 | 用户经验 |
| E | 二手汇总、匿名转载 | 线索 |

等级越低，不代表完全没用，而是：

> 不适合单独支撑强结论。

## 原始来源优先

例如一篇媒体文章写：

```text
Product X supports Wi-Fi 7.
```

如果它引用官方规格，优先回到：

```text
官方规格
```

而不是继续引用媒体。

原则：

```text
Secondary Source
→
找到 Original Source
→
优先验证原始事实
```

## 第一手证据

第一手证据包括：

- 自己实测
- 自己拍摄
- 自己部署
- 自己采样
- 自己 Benchmark
- 自己采访

但必须记录条件。

例如：

```text
Model A = 38 tok/s
```

至少说明：

| 条件 | 示例 |
| --- | --- |
| Hardware | RTX 5090 |
| Quantization | 4-bit |
| Context | 4K |
| Software | Version X |
| Date | 2026-09 |

否则数字很难复现。

## 独立性

10 个页面重复同一个新闻稿，不等于 10 份证据。

例如：

```text
Brand Release
├─ Media A
├─ Media B
└─ Blog C
```

实际原始来源只有：

```text
1
```

所以内部建议记录：

| 字段 | 用途 |
| --- | --- |
| source_id | 原始来源 |
| publisher | 发布者 |
| original_source | 是否原始 |
| independence_group | 是否同源 |
| published_at | 时间 |
| evidence_type | 规格 / 测试 / 观点 |

## 相关性

高权威来源不等于对所有 Claim 都有用。

例如：

```text
政府网站
```

权威很高，但不一定适合证明：

```text
某 GPU 游戏性能
```

证据必须同时满足：

```text
Authority
+
Topical Relevance
```

## 时效性

同一来源会随时间失效。

| 内容 | 时效风险 |
| --- | ---: |
| 基础数学 | 低 |
| 协议标准 | 中 |
| 软件版本 | 高 |
| 产品价格 | 极高 |
| API | 极高 |
| 法规 | 高 |

所以证据等级还要加：

```text
Freshness
```

## 证据冲突

如果不同来源冲突，不要直接挑一个喜欢的。

建议：

| 步骤 | 动作 |
| --- | --- |
| 1 | 找原始来源 |
| 2 | 检查日期 |
| 3 | 检查版本 |
| 4 | 检查测试条件 |
| 5 | 判断是否其实适用于不同场景 |
| 6 | 无法解决时明确写冲突 |

例如：

```text
Source A:
120Hz

Source B:
144Hz
```

可能是：

```text
不同 Firmware
不同接口
不同 SKU
```

## 证据链

复杂 Claim 最好不是单点证明。

例如：

```text
240Hz
→ improves responsiveness
```

可以拆：

| 子边 | 证据 |
| --- | --- |
| 240Hz → 4.2ms interval | 数学 |
| 更短间隔 → 更多刷新机会 | 显示机制 |
| 高 FPS → 更容易利用 | 场景条件 |

多条子边共同支持父结论。

## 内部评分

可以定义：

```text
Evidence Score
=
Quality 35%
+
Relevance 25%
+
Independence 20%
+
Freshness 20%
```

不是搜索引擎官方指标，只用于 QA。

## 红线

| 行为 | 风险 |
| --- | --- |
| 二手转载当原始证据 | 高 |
| 一个样本推行业结论 | 高 |
| 未披露品牌赞助 | 高 |
| 使用过期规格 | 高 |
| 伪造 Benchmark | 极高 |
| AI 摘要无原始来源 | 高 |

## QA 表

| 检查 | 合格 |
| --- | --- |
| Claim 有证据 | 是 |
| 证据直接相关 | 是 |
| 强 Claim 用强证据 | 是 |
| 原始来源优先 | 是 |
| 来源独立性已确认 | 是 |
| 日期有效 | 是 |
| 测试条件明确 | 是 |
| 利益关系披露 | 是 |

## 核心规范

```text
先定义 Claim
→
判断所需证据等级
→
寻找原始来源
→
检查独立性
→
检查时效性
→
再决定语言强度
```

> **来源与证据等级的目标不是“引用更多”，而是保证每一个重要结论都有与其风险和强度相匹配的证据。**
